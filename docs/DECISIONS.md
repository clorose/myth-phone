# MythPhone 개발 결정 기록

## 2026-07-25

### 버블톡은 실제 채팅, 메시지는 연출용 기록

두 앱은 화면만 다른 것이 아니라 데이터의 성격 자체를 다르게 가져간다.

- 버블톡: 실제 대화 전용. 플레이어와 GM(NPC 명의 포함)이 실시간으로 주고받는 살아있는 채팅이다. 완성형은 `ChatMessage` 귓속말 기반으로 구현하며, 현재 `data/bubbletalk.json` 더미 데이터는 실채팅 실장 시점에 제거한다.
- 메시지: 연출용 기록 전용. GM이 시나리오마다 미리 깔아두는 문자 기록(조사 중 발견한 폰에 남아 있는 대화 등)으로, 실시간 전송이 필요 없다. 지금의 데이터 기반 구조가 완성형에 가깝다. 다만 모듈 안 JSON은 GM이 파일을 직접 고쳐야 하므로, 장기적으로 월드 데이터로 옮겨 UI에서 편집하는 방향을 검토한다.

## 2026-07-24

### 프로젝트 이름

초기 작업명은 `Smartphone`이었으나 가상 스마트폰 제품명처럼 들리는 `MythPhone`으로 확정했다.

- 표시 이름: `MythPhone`
- 모듈 ID: `myth-phone`
- 코드 파일: `scripts/myth-phone.js`
- 스타일 파일: `styles/myth-phone.css`

### 지원 환경

로컬에 설치된 Foundry VTT `14.365`를 기준으로 개발한다.

### 파일 배치

WSL에서 개발 성능을 유지하기 위해 실제 프로젝트는 `/home/heun1/FVTT/myth-phone`에 둔다. Windows Foundry의 모듈 폴더에는 WSL 프로젝트를 가리키는 Windows 심볼릭 링크를 둔다.

Linux 방식 링크는 Windows Foundry에서 열리지 않았으므로 사용하지 않는다.

### UI 우선 개발

서버 통신과 영구 저장보다 전체 앱 UI와 화면 흐름을 먼저 완성한다. 현재 메시지 입력은 프론트엔드 동작 확인을 위한 임시 기능이다.

### 디자인 방향

아이폰 계열 스마트폰을 강하게 연상시키는 디자인을 목표로 한다. 단, 공개 저장소 배포를 고려해 Apple에서 추출한 에셋, 로고, 공식 앱 아이콘과 공식 제품을 자처하는 표현은 포함하지 않는다.

이 제한은 아래의 `디자인 레퍼런스 범위` 결정으로 대체되었다.

### 향후 통신

플레이어 간 실시간 메시지에는 별도 서버 대신 Foundry의 `game.socket`을 사용한다. 메시지 이력은 소켓과 별도로 영구 저장해야 한다.

### 디자인 레퍼런스 범위

초기의 공개 저장소 배포를 전제로 한 디자인 제한은 현재 작업 방침으로 사용하지 않는다. 구체적인 레퍼런스, 명칭, 클론 범위와 에셋 사용 여부는 사용자가 프로젝트 목적에 맞게 결정한다.

### 메시지와 버블톡

기본 `메시지` 앱과 `버블톡`은 별도의 앱과 데이터 구조로 유지한다.

- 메시지: 전화번호 기반 기본 문자
- 버블톡: 친구와 채팅방 기반 모바일 메신저
- 현재 UI 더미 데이터는 `data/messages.json`과 `data/bubbletalk.json`으로 분리한다.
- 완성형 버블톡은 Foundry `ChatMessage` 귓속말과 모듈 플래그를 기반으로 구현한다.
- NPC 발신자는 별도 가상 계정이 아니라 GM이 선택한 Foundry Actor 또는 Token을 `ChatMessage.speaker`로 사용한다.

### 전화의 역할

전화는 장시간 자유 대화나 분기 대화 엔진으로 만들지 않는다. 스마트폰 기본 앱의 분위기를 유지하면서 GM이 특정 플레이어에게 짧고 긴급한 NPC 내레이션을 전달하는 연출 기능으로 사용한다.

- 기본 테스트 장면은 `data/call-scenes.json`에 저장한다.
- GM이 NPC Actor, 대상 플레이어와 장면을 선택해 발신한다.
- 대상 플레이어에게만 벨소리, 수신 화면과 장면을 표시한다.
- 상세 대본 대신 발신자, 시각과 수신 여부만 최근 통화에 남긴다.

### 이미지 단서

이미지 단서는 메시지, 버블톡 또는 이메일의 원본 문맥에서 직접 확인한다. 출처와 설명 없이 이미지만 모으는 독립 사진 앱은 현재 개발하지 않는다. 향후 통합 보관이 필요하면 발신자, 원본 메시지와 출처 링크를 유지하는 증거 보관함을 검토한다.
