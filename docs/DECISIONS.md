# MythPhone 개발 결정 기록

## 2026-07-25

### 버블톡은 실제 채팅, 메시지는 연출용 기록

두 앱은 화면만 다른 것이 아니라 데이터의 성격 자체를 다르게 가져간다.

- 버블톡: 실제 대화 전용. 플레이어와 GM(NPC 명의 포함)이 실시간으로 주고받는 살아있는 채팅이다. 완성형은 `ChatMessage` 귓속말 기반으로 구현하며, 현재 `data/bubbletalk.json` 더미 데이터는 실채팅 실장 시점에 제거한다.
- 메시지: 연출용 기록 전용. GM이 시나리오마다 미리 깔아두는 문자 기록(조사 중 발견한 폰에 남아 있는 대화 등)으로, 실시간 전송이 필요 없다. 지금의 데이터 기반 구조가 완성형에 가깝다. 다만 모듈 안 JSON은 GM이 파일을 직접 고쳐야 하므로, 장기적으로 월드 데이터로 옮겨 UI에서 편집하는 방향을 검토한다.

### 버블톡 실채팅 전환 설계

세 계층으로 나눠 전환한다.

- 데이터 계층: 방 메타는 `{roomId, type, participantUserIds, npcActorUuid?, name}`을 월드 범위에 저장하고, 쓰기는 GM 권한이므로 socketlib로 GM에게 위임한다. 메시지는 별도 저장소를 만들지 않고 Foundry `ChatMessage` 귓속말을 사용한다(`whisper`에 참여자 ID, `flags.myth-phone`에 `app`과 `roomId`). 시간은 timestamp로 저장하고 표시할 때만 포맷한다. 안읽음은 사용자별 `lastReadTimestamp` 하나로 계산한다.
- 상태·렌더 계층: 전면 innerHTML 재렌더 대신 스토어와 부분 렌더로 분리한다. `createChatMessage` 훅에서 해당 방이 열려 있으면 말풍선만 append, 아니면 목록 항목과 배지만 갱신한다. 사용자 텍스트는 전부 이스케이프를 거친다. 전송은 DOM 직접 추가가 아니라 `ChatMessage.create` 후 훅으로 되돌아와 그려지는 단일 경로로 처리한다.
- 작업 순서: ① 렌더러 리팩터(스토어 분리·부분 렌더·이스케이프·timestamp, 더미 데이터 유지) ② 1:1 방 ChatMessage 연동(전송·수신·영속) ③ 방 생성·참여자 필터·사용자별 안읽음 ④ NPC 대화(Actor speaker, GM 발신 UI) ⑤ 단체톡 확장(초대·나가기). ①이 나머지 전부의 토대이며 UI 외형 변경 없이 진행할 수 있다.

### 공통 계층 분리

렌더러가 공유하는 기반을 세 모듈로 분리했다.

- `scripts/utils.js`: HTML 이스케이프, 시간 표시(`formatTime`은 timestamp 숫자만 포맷하고 더미 문자열은 통과), 통화 시간 포맷.
- `scripts/store.js`: 앱 데이터 로드·보관과 변경 알림(pub/sub). 렌더러는 스토어에서 읽고, 이후 ChatMessage 훅이 스토어를 갱신하는 구조를 전제한다.
- `scripts/socket.js`: `game.socket` 모듈 채널 하나에 타입별 핸들러 라우팅. 각 핸들러는 수신 즉시 대상 사용자 ID를 검사하고 무관한 이벤트를 폐기한다.

사용자 입력과 Actor 이름 등 외부 문자열은 렌더링 시 전부 이스케이프를 거친다. 새로 만드는 메시지의 시간은 표시 문자열이 아니라 timestamp로 저장한다.

### 버블톡 1:1 실채팅 구조

- 1:1 방 ID는 `direct:` 뒤에 두 사용자 ID를 정렬해 붙인 값으로, 방 생성 절차 없이 사용자 쌍마다 자동으로 정해진다.
- 메시지 원본은 Foundry `ChatMessage` 귓속말이다. `whisper`에 상대 사용자 ID, `flags.myth-phone`에 `app`과 `roomId`를 넣는다. 월드 문서라 영속과 실시간 전달을 Foundry가 처리한다.
- 접속 시 `game.messages`에서 참여 중인 방을 복원하고, 이후에는 `createChatMessage` 훅으로 스토어를 갱신한다. 참여자(작성자 포함)가 아닌 클라이언트는 반영하지 않고 폐기한다.
- 전송은 DOM에 직접 그리지 않고 `ChatMessage.create` 후 훅으로 되돌아와 그려지는 단일 경로다.
- 친구 탭은 더미 친구 대신 실제 Foundry 사용자 목록을 표시한다. 채팅 탭에는 실제 방을 더미 위에 표시하며, 더미는 단체톡 실장 시 제거한다.
- 버블톡 귓속말은 Foundry 기본 채팅 사이드바에도 귓속말로 표시된다. 구분 표시나 숨김은 이후에 판단한다.

### 브라우저는 뷰어, 페이지는 정적 HTML

- 브라우저 앱은 페이지를 직접 만들지 않는다. GM이 만든 정적 HTML 파일(Foundry `Data/` 안, 예: `worlds/월드명/sites/`)을 iframe으로 표시하는 뷰어다.
- fetch로 HTML을 받아 DOM에 삽입하는 방식은 페이지 CSS/JS가 Foundry·폰 UI와 충돌하므로 쓰지 않는다. iframe(sandbox)으로 격리한다.
- 등록 사이트 목록은 월드 설정에 저장해 전원이 공유하고, 등록·삭제는 GM만 한다.
- 사이트마다 다른 UI는 템플릿으로 흉내 내지 않고 실제 별개 페이지로 해결한다. 자주 쓰는 유형의 템플릿은 제작 보조 도구로 추후 검토한다.

### 대화 프라이버시와 로그

- 플레이어끼리의 버블톡(개인톡·단체톡)은 GM에게 인게임에서 보이지 않는다. Foundry 귓속말 기본 동작(작성자·수신자만 열람, GM 포함 제3자 불가)을 그대로 따른다.
- **유저 간 개인톡은 어떤 방식으로도 본인들 공개 없이는 노출되지 않는다.** GM의 방 단위 내보내기와 통합 로그에서도 제외되며, 참여자 본인이 자기 방을 내보내 제공할 때만 공개된다.
- GM의 로그 내보내기 대상: 기본 채팅과 NPC↔유저 방은 기본 포함(배포용 로그 정리의 핵심), 단체톡은 옵션(체크박스, 기본 꺼짐).
- 플레이어는 자기가 참여한 방만 내보낼 수 있다.

### 안읽음·단체톡·연락처 구조

- 읽음 상태: 사용자별 `lastRead`(방 ID → 마지막 읽은 시각)를 유저 플래그에 저장한다. 유저 플래그는 모두에게 보이므로 상대의 읽음 여부(보낸 메시지 옆 숫자)도 플래그 조회로 계산하고, `updateUser` 훅으로 실시간 갱신한다.
- 통화 기록: 사용자별 유저 플래그에 최근 50건 저장.
- 단체톡: 방 ID는 `group:{randomID}`. 방 메타(이름·참여자 ID 목록)는 모든 단체 메시지의 플래그에 실어 어느 메시지에서든 방을 복원할 수 있게 한다.
- 연락처: NPC 전화번호는 Actor의 `myth-phone.contact` 플래그에 저장한다. 플레이어가 NPC 연락처에서 대화를 시작하면 `npc:{actorId}:{자기 userId}` 방이 열리고 답장 규칙은 NPC 개인톡과 같다. NPC 연락처는 현재 모든 사용자에게 보이며, 노출 범위 제한(아는 NPC만 표시)은 이후 결정한다.

### NPC 개인톡 구조

- 방 ID는 `npc:{actorId}:{userId}`. GM이 버블톡의 NPC 명의 대화 화면에서 NPC와 대상 플레이어를 골라 연다.
- 발신 NPC 목록에는 월드에 존재하는 Actor 중 플레이어 소유가 아닌 것만 표시한다. 존재하지 않는 캐릭터 명의로는 보낼 수 없다. 전화 발신 화면도 같은 필터를 쓴다.
- GM 발신 메시지는 대상 플레이어에게 귓속말로 가고 `speaker.alias`에 Actor 이름을 넣는다. 화면 표시 이름은 `speaker.alias`를 우선한다.
- 플레이어 답장은 GM 전원에게 귓속말로 보내고 같은 roomId에 연결한다.
- GM 화면의 방 이름은 `NPC 이름 → 플레이어 이름`, 플레이어 화면에서는 NPC 이름만 표시한다.

### NPC 전화 소켓 발신

- GM은 전화 앱의 발신 화면에서 NPC Actor, 대상 플레이어, 전화 장면을 선택해 발신한다.
- `incoming-call` 이벤트는 모든 클라이언트에 전달되지만 대상 사용자만 처리하고 나머지는 폐기한다. 대상 클라이언트는 폰을 자동으로 열고 수신 화면과 벨소리를 표시한다.
- 장면 대본은 소켓으로 보내지 않고 `sceneId`만 보내 각 클라이언트의 `call-scenes.json`에서 조회한다.
- 응답·거절 결과는 `call-result` 이벤트로 보고하고 GM에게만 알림으로 표시한다.
- 통화 기록은 발신자·시각·수신 여부만 남기며, 현재는 클라이언트 세션 메모리에 보관한다. 영구 저장은 별도 단계.

### 프로젝트 이름

초기 작업명은 `Smartphone`이었으나 가상 스마트폰 제품명처럼 들리는 `MythPhone`으로 확정했다.

- 표시 이름: `MythPhone`
- 모듈 ID: `myth-phone`
- 코드 파일: `scripts/myth-phone.js`
- 스타일 파일: `styles/myth-phone.css`

### 지원 환경

로컬에 설치된 Foundry VTT `14.365`를 기준으로 개발한다.

### 파일 배치

WSL에서 개발 성능을 유지하기 위해 실제 프로젝트는 `/home/heun1/FVTT/myth-phone`에 둔다. Windows Foundry의 모듈 폴더에는 WSL 프로젝트를 가리키는 Windows 심볼릭 링크를 둔다.

Linux 방식 링크는 Windows Foundry에서 열리지 않았으므로 사용하지 않는다.

### UI 우선 개발

서버 통신과 영구 저장보다 전체 앱 UI와 화면 흐름을 먼저 완성한다. 현재 메시지 입력은 프론트엔드 동작 확인을 위한 임시 기능이다.

### 디자인 방향

아이폰 계열 스마트폰을 강하게 연상시키는 디자인을 목표로 한다. 단, 공개 저장소 배포를 고려해 Apple에서 추출한 에셋, 로고, 공식 앱 아이콘과 공식 제품을 자처하는 표현은 포함하지 않는다.

이 제한은 아래의 `디자인 레퍼런스 범위` 결정으로 대체되었다.

### 향후 통신

플레이어 간 실시간 메시지에는 별도 서버 대신 Foundry의 `game.socket`을 사용한다. 메시지 이력은 소켓과 별도로 영구 저장해야 한다.

### 디자인 레퍼런스 범위

초기의 공개 저장소 배포를 전제로 한 디자인 제한은 현재 작업 방침으로 사용하지 않는다. 구체적인 레퍼런스, 명칭, 클론 범위와 에셋 사용 여부는 사용자가 프로젝트 목적에 맞게 결정한다.

### 메시지와 버블톡

기본 `메시지` 앱과 `버블톡`은 별도의 앱과 데이터 구조로 유지한다.

- 메시지: 전화번호 기반 기본 문자
- 버블톡: 친구와 채팅방 기반 모바일 메신저
- 현재 UI 더미 데이터는 `data/messages.json`과 `data/bubbletalk.json`으로 분리한다.
- 완성형 버블톡은 Foundry `ChatMessage` 귓속말과 모듈 플래그를 기반으로 구현한다.
- NPC 발신자는 별도 가상 계정이 아니라 GM이 선택한 Foundry Actor 또는 Token을 `ChatMessage.speaker`로 사용한다.

### 전화의 역할

전화는 장시간 자유 대화나 분기 대화 엔진으로 만들지 않는다. 스마트폰 기본 앱의 분위기를 유지하면서 GM이 특정 플레이어에게 짧고 긴급한 NPC 내레이션을 전달하는 연출 기능으로 사용한다.

- 기본 테스트 장면은 `data/call-scenes.json`에 저장한다.
- GM이 NPC Actor, 대상 플레이어와 장면을 선택해 발신한다.
- 대상 플레이어에게만 벨소리, 수신 화면과 장면을 표시한다.
- 상세 대본 대신 발신자, 시각과 수신 여부만 최근 통화에 남긴다.

### 이미지 단서

이미지 단서는 메시지, 버블톡 또는 이메일의 원본 문맥에서 직접 확인한다. 출처와 설명 없이 이미지만 모으는 독립 사진 앱은 현재 개발하지 않는다. 향후 통합 보관이 필요하면 발신자, 원본 메시지와 출처 링크를 유지하는 증거 보관함을 검토한다.
